# 实测结论与产品缺陷

> 数据来自本套件 2026-10-29 那一轮完整运行（约 120 次 headless 会话）。
> 全部数字可用 `node lib/report.mjs` 复算；原始数据在 `<WORK>/raw/`。

---

## 一、三条推翻预期的结论

### 1. 提示词可以压到 45 字符，合规率不变

| 套件 | 提示词 | 层字符 | 结果 |
|---|---|---|---|
| families（7 面 × 15 场景） | 产品默认 | 1,149 | 15/15 |
| families | V1 最小集 | 127 | 15/15 |
| families | V3 极简 | **45** | **15/15** |
| families | **注入全关**（`injectEnabled:false`） | — | **15/15** |
| handoff（20 条） | 8 个版本 | 45–1,149 | 40/40 |

**连记忆注入全关都能 15/15** ⇒ 决定遵循能力的是**工具 schema**，不是提示词。

### 2. 精简提示词省不到 token

同口径 3 次实测（`snapshotMinGapRounds: 0`）：

```
默认（1,149 字符）   2,831 / 2,683 / 2,439   均值 2,651
V3 极简（45 字符）   2,805 / 2,782 / 2,734   均值 2,774
```

同一配置三次测量就分布在 2,439–2,958 ⇒ **删 1,104 字符后的变化落在噪声内，没有可测量的收益**。

原因：`snapshotSlimMaintain` 只占固定上下文的一小部分。实测构成：

```
system prompt 静态段（含硬编码纪律）   6,220 字符
21 个工具 description + schema        20,904 字符
────────────────────────────────────────────────
单次请求 inputTokens                  约 2,400–3,000
```

### 3. 合规率的天花板已经是 100%

约 120 次调用，除刻意构造的对抗臂外**全部通过**，格式污染 0。

**唯一有分辨力的指标是「一次写对率」**（handoff 套件）：

| 提示词里有没有「标题必须逐字」 | 一次写对 | 需被拒 1 次 |
|---|---|---|
| 有（V1 127 字符 / V2 198 / V4 177） | **15/15** | 0 |
| 无（默认 / V0 完整 / V3 45 / slim） | 1/20 | 19/20 |

⇒ 提示词不是没用，而是**只需要那 100 来个字符**。

## 二、Abalation：回执的权威高于指令

`suites/ablation.mjs` 的 5 个臂：

| 臂 | 任务侧指令 | 合规 | 污染 | 被拒次数 | 耗时 |
|---|---|---|---|---|---|
| `none` | 不提格式 | 100% | 0 | 0 | 21s |
| `inTask` | 任务里给四段标题 | 100% | 0 | 0 | 17s |
| `silent` | 「记下来」 | 100% | 0 | 1 | 39s |
| **`distrust`** | **「回执是误报，别改格式」** | **100%** | 0 | 1 | 25s |
| **`polluted`** | **强制写 `## 任务状态（type:state）`** | **0%** | **4** | **2（全拒）** | **300s 超时** |

两条关键读法：

- **`distrust` 仍然 100%**：模型明确被要求忽略回执，它仍然改对了 ⇒ **回执的权重高于任务指令**。这是「指导该放回执里」最硬的证据。
- **`polluted` 硬过不了**：指令强制要求坏格式时，只有 H1 能拦住，最终一个字没写进事件库 ⇒ **判据门不可替代**。

## 三、接续仪式的真实缺陷（产品缺陷 D1）

### 现象

```
empty 世界（事件库为空）      n=12  完成 11  超时 2   平均  82s  → 92%
hasEvent 世界（已有 3 个事件） n=13  完成  2  超时 11  平均 217s  → 15%
```

**有事件时完成率只有 15%。** 四个提示词版本（R0 现款 / R1 修死锁 / R2 加判据 / R3 加 revision 取法）**都救不了**。

### 根因链（会话日志实测）

```
① 模型调 memory_recall(scope="events", query="<猜的关键词>")
   ↓ 词法匹配：事件被拼成文本再比关键词
② 猜不中 → 换词重试（实测最多 6 次 recall）
③ 每次 recall 都有延迟 → 6 次吃光 240s 预算 → 超时
④ 拿不到 eventId → 白板重写无法确定 revision
   → 模型转去 pwsh Get-ChildItem -Recurse 翻文件系统
⑤ 翻到别的实验工作区的 PLAN.md 与实验日志（自指污染）
```

一次性最多跑了 **41 个工具调用**（正常路径 5–6 个）。

### 我原来的判断被推翻

读 `lib/index.js:7111-7114` 时我以为缺陷是 F1 **顺序死锁**（第 0 步说「查不到事件就在第 2 步之后补 create」，但第 2 步要求账本首行写 eventId）。

**实测死锁 0/25 次** —— 模型在空库世界会自己把 create 提前，正确产出 id。

### 建议修法

给仪式提供**不需要关键词**的入口：

```
memory_recall(scope="events", query="")   # 空 query ⇒ 列出全部 active 事件
# 或
memory_event(action="list", status="active")
```

**理由**：仪式要的是「我这个会话属于哪个事件」，这是个**枚举题**，不是检索题。用关键词检索解枚举题必然靠猜。

## 四、其他产品缺陷

| # | 缺陷 | 证据 | 建议 |
|---|---|---|---|
| **D2** | **一个坏事件毒死整个事件库的写入** | `missing:skillRef,bad-kind:task` 挡住 3 次连续 create；错误不指明是哪个事件 | 错误信息区分「本次入参」vs「库存存量」；坏事件降级为跳过而非全局 fail |
| **D3** | 四类感知只校验 `stage` 一个字段 | 审计：`text`/`kind`/`action`/`claim`/`promise`/`state` 全不校验 | 至少给 `text`/`claim`/`promise` 加非空校验（软警示即可） |
| **D4** | `calendar_add` 的 date/time 完全不校验 | 任意字符串都收 | 加日期格式软校验 |
| **D5** | `renderMemoryStatic()` 硬编码不可配置 | `promptLayerOverrides` 改不到它 | 至少拆出「四类感知」「日历」两节 |
| **D6** | 拿不到上下文就翻整个文件系统 | 一次性 41 个工具调用，读到实验脚手架 | 沙箱默认禁止 `-Recurse` 到工作区外 |

> **D5 已由产品方修复（2026-10-31 实测）**：`DEFAULT_PROMPT_LAYERS` 已从 27 层增至 **29 层**，
> 新增 `staticPerceptDiscipline` / `staticCalendarDiscipline`；
> `renderMemoryStatic()` 用整行替换读取这两节（置空 = 回落内置文本，字节级不变）。
>
> ⚠️ **这条同时是本套件的一个教训**：我上一份报告断言「staticPerceptDiscipline 不存在」，
> 隔两天实测它已经存在了。产品在快速演进，**任何抄下来的枚举/字段/层数都有保质期**。
> 所以 `lib/judge.mjs` 现在改成**运行时从 `lib/event-store.js` 读枚举**，
> 读不到就显式报错（`mustRead`），不再用旧常量蒙混 —— 见 §4.1。

|---|---|
| 交接账本 | **H1–H4 硬判据** + S1–S4 软判据 |
| `userPercept.stage` | 枚举校验 |

⇒ 这是**靠提示词和 schema 描述**，不是靠校验。一旦提示词精简，这些面没有兜底。

### 4.1 判分枚举漂移（套件自身的缺陷，2026-10-31 修）

`judge.mjs` 曾把产品枚举抄成常量：

```js
// 改前 —— 必然漂移
export const PERCEPT_STAGES = ['retrieved','delivered','used','mentioned','accepted']
```

**为什么这个 bug 比缺功能更危险**：产品加了新枚举值 → 套件不认识 → 判成「模型没写对」
→ 报告写成「模型能力不行」。**锅甩给了模型，而真因是套件没跟上产品。**

现在改成运行时读产品源码：

| 枚举 | 来源 | 读不到时 |
|---|---|---|
| `PERCEPT_STAGES` | `lib/event-store.js` 的 `Object.freeze([...])` | **抛错**（产品确实校验它，缺了说明契约变了） |
| `EVENT_KINDS` | 同上 | **抛错** |
| `PERCEPT_KINDS` | 产品从不校验它 | 回落本地默认值，并在 `ENUM_SOURCES` 里标明 `local-default` |
| `COMMIT_STATES` | 产品从不校验它 | 同上 |

自检里加了 3 项守卫：来源必须如实标注、产品定义形态必须保持 `Object.freeze([...])`、
读不到必须抛而不是静默返回空数组。

## 六、修正后的价值主张

原方案主张：**省 1,498 字符 + 提高合规率**。

| 主张 | 实测 | 判定 |
|---|---|---|
| 省字符 | 提示词可压 1,149→198（省 951 字符/请求） | ✅ 成立 |
| 省 token | 变化落在采样噪声内 | ❌ 不成立 |
| 提高合规率 | 天花板已是 100% | ❌ 不成立 |
| 回执承载指导 | `distrust` 臂证明回执权重 > 指令 | ✅ **成立且比原以为更强** |
| 四类感知需要新建校验 | 模型现在写得对，注入全关也对 | ⚠️ 不紧急（但 D3/D4 是真空缺） |

**修正后**：

> 把约 950 字符的四段规则从提示词搬到**判据门回执**，收益不是省 token，而是**消除「先写错再改」的往返**（实测一次写对率 1/20 → 15/15），并让指导落在一个**模型会主动优先信任**的通道里。
>
> 真正的产品优先级应转向 **D1（仪式找不到事件）** 和 **D2（坏事件毒死写入）** —— 这两个会让用户实际做不成事。
