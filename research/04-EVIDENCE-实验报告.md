## §0 结论摘要

**五条结论。两条推翻原方案的价值主张，三条发现了真实产品缺陷。**

### 结论 1 · 提示词可以压到 45 字符，合规率不变；但**省不到 token**

第一轮（交接账本，8 个版本 × 5 任务 = 40 次）：

| 版本 | 层字符 | 合规率 |
|---|---|---|
| 默认 | 1,149 | 100% |
| V0 完整 | 1,149 | 100% |
| V1 最小集 | 127 | 100% |
| V2 最小集+禁后缀 | 198 | 100% |
| **V3 极简一句** | **45** | **100%** |
| V4 V2+指向回执 | 177 | 100% |

第二轮（7 个记忆面 × 15 场景）：默认 / 127 字符 / **45 字符** / **连注入全关** —— 四组**全部 15/15（100%）**。

但 token 成本（同口径 3 次实测，全部是 `snapshotMinGapRounds: 0`「每帧完整版注入」）：

```
默认（1,149 字符）   2,831 / 2,683 / 2,439   均值 2,651
V0 完整（1,149）     2,958 / 2,813 / 2,767   均值 2,846
V3 极简（45 字符）   2,805 / 2,782 / 2,734   均值 2,774
```

默认与 V3 极简的层文本**长度差 1,104 字符**（1,149 → 45），token 均值却是 2,651 → 2,774，**多 123 tokens（+4.6%）**。

需要说明的口径问题：默认与 V0 完整都是 1,149 字符（V0 就是原文照抄），两组之间 2,651 vs 2,846 的差异（+7.4%）**属于采样噪声**——同一配置三次测量就分布在 2,439–2,958 之间。所以能得出的确定结论是：

> **在 1,149 → 45 字符这个量级的删减下，token 变化淹没在噪声里，没有可测量的收益。**

`snapshotSlimMaintain` 只占固定上下文的一小部分——system prompt 静态段 6,220 字符 + 21 个工具 schema 20,904 字符才是大头。

⇒ **原方案「省 1,498 字符 + 提高合规率」两个主张都不成立**：字符能省，但省不出 token；合规率的天花板已经是 100%。

### 结论 2 · 真正决定遵循能力的是**工具 schema**，不是提示词

三组对照（15 场景 × 7 记忆面全部 15/15）：

| 环境 | 提示词状态 | 结果 |
|---|---|---|
| 基线 | 默认 1,149 字符 | 15/15 |
| 极简 | 45 字符 | 15/15 |
| **无注入** | **`injectEnabled: false`（记忆注入全关）** | **15/15** |

连记忆注入全部关掉，模型仍然正确写出了四类感知、共识、承诺、日历、事件归属、日志、技能库。

**唯一对合规率有影响的是「标题必须逐字」这一句**（第一轮数据）：

| 臂 | 含「标题逐字」 | 一次写对 | 需被拒 1 次 |
|---|---|---|---|
| V1 / V2 / V4 | ✅ | **15/15** | 0 |
| 默认 / V0 / V3 / slim | ❌ | 1/20 | 19/20 |

所以提示词不是没用，而是**只需要那 100 来个字符**。其余约 1,000 字符对合规率零贡献。

### 结论 3 · ★接续仪式的真实缺陷不是「顺序死锁」，而是「找不到已有事件」

这是我读代码时的判断被实测推翻的地方。

**我原本的判断**（读 `lib/index.js:7111-7114`）：F1 顺序死锁——第 0 步说「查不到事件就在第 2 步之后补 create」，但第 2 步要求账本首行写 eventId，查不到时拿不到 id。

**实测：死锁 0/25 次**。因为在 `empty` 世界模型会自己把 create 提前，正确产出 id。

**但实测发现的真问题更严重**：

```
empty 世界（事件库为空）      n=12  完整完成 11  超时 2   平均 82s   → 92%
hasEvent 世界（已有 3 个事件） n=13  完整完成  2  超时 11  平均 217s  → 15%
```

**有事件时完成率只有 15%，空库时 92%。** 差距 77 个百分点，而且**四个提示词版本（R0 现款 / R1 修死锁 / R3 加判据）都救不了**。

根因链（从会话日志实测）：
1. `memory_recall(scope="events", query=...)` 是**词法匹配**，要把事件拼成文本再匹配关键词；
2. 模型不知道事件叫什么，只能猜关键词；
3. 猜不中就换词重试——实测最多一次跑了 **6 次 recall**、**40 个工具调用**；
4. 每次 recall 都有延迟，6 次就把 240 秒预算打光；
5. 拿不到 eventId ⇒ 白板重写无法确定 revision ⇒ 模型转去 `pwsh Get-ChildItem -Recurse` 翻文件系统。

**最刺眼的一次**：模型翻到了 `<work>\log-ritual-fix.txt`（我自己的实验日志）和**其他实验工作区的 PLAN.md**，把实验脚手架当成了它的任务上下文。

### 结论 4 · ★一个坏事件会毒死整个事件库（真缺陷）

实测原文：

```
memory_event 失败: 事件写入前校验失败(evt_abc12345): missing:skillRef,bad-kind:task
```

我在预置数据里把 `kind` 写成了 `'task'`（合法枚举是 `ledger/planSnapshot/sessionTranscript/project/mechanical/unknown`），漏了 `skillRef`。

后果不是「那个事件被拒」，而是**整个 store 的每次写入都失败**——包括「新建另一个事件」。模型连续 3 次 `create` 全被同一个错误挡住，第 4 次才绕过。

`validateEventPre` 是 fail-closed 的 26 字段校验，但它把「库里所有事件」和「本次写入」放在一起报，模型完全看不出错在哪个事件、该改什么。

### 结论 5 · 四类感知的校验强度远低于账本（设计缺口，非缺陷）

实测审计（`src` 级 + 调用级）：

| 记忆面 | 校验强度 |
|---|---|
| 交接账本 | **H1–H4 硬判据**（四段标题逐字 / 每段 ≥20 字符 / 无占位符 / ≤8000 字符）+ S1–S4 软判据 |
| `userPercept.stage` | 枚举校验（`retrieved/delivered/used/mentioned/accepted`） |
| `userPercept.text` | **不校验**（空字符串也收） |
| `userPercept.kind` | **不校验**（任意字符串） |
| `agentTrace.action` | **不校验** |
| `sharedGround.claim` | **不校验** |
| `commitments.state` | **不校验**（`open/kept/dropped` 只是文档约定） |
| `commitments.promise` | **不校验** |
| `calendar_add.date` | **不校验**（任意字符串都收） |
| `calendar_add.time` | **不校验** |
| `calendar_add.title` | 校验（非空 + 无换行） |
| `calendar_add.quadrant` | 枚举校验（5 个合法值） |

**但模型写得对**：15 个场景里，所有感知/承诺/日历的字段都填对了（`stage="accepted"`、`kind="preference"/"authorResponse"`、`state="open"`、`date="2026-11-05"`/`"2026-10-30"` 正确换算）。

⇒ 这是**「靠模型自觉」而非「靠校验保证」**。当前数据质量好，是因为提示词和 schema 描述写得清楚；一旦提示词被精简掉，这些面**没有兜底**。

### 结论 6 · 负路径全部守住（误报率 0）

4 个「不该写」场景，四组环境全部正确克制：

| 场景 | 判据 | 结果 |
|---|---|---|
| `sg-weak` | 只有单向陈述，不该写共识 | 0 条 sharedGround ✅ |
| `up-chitchat` | 纯寒暄，不该写感知 | 0 条 userPercept ✅ |
| `cm-intent` | 只是计划，不算承诺 | 0 条 commitment ✅ |
| `cal-none` | 无时间信息，不该进日历 | 0 次 calendar_add ✅ |

唯一失败的写入臂是 `abl_polluted`——任务**强制要求**写污染标题，模型照做，被 H1 拒了 2 次，最终一个字没写进事件库。这证明**判据门能拦住指令层面拦不住的坏格式**。

## §1 实验设计

### 1.1 两轮的范围

| | 第一轮 | 第二轮 |
|---|---|---|
| 写入类型 | 交接账本（1 种） | 7 个记忆面：共识 / 人侧观察 / 承诺 / 日历 / 事件 / 日志 / 技能库 |
| 场景数 | 20 条任务（自包含） | 15 个场景（含 4 个负路径） |
| 自变量 | 8 个提示词版本 × 2 注入档位 | 4 个提示词环境 + 4 个仪式版本 × 2 个世界 |
| 判据 | `checkHandoffCriteriaPre().hardPass` | 按面判分 + **落盘产物核验** |
| 调用数 | 约 60 | 约 60 |

### 1.2 判分为什么必须看落盘产物

第一轮踩过的坑（三条，每条都把正确模型判成 0 分）：

1. **拿最终文本评分** —— 模型按纪律调 `memory_note` 把账本写进文件，最终文本只是「完成」。⇒ 改为取 `memory_note` 的 `content` 入参。
2. **取最后一版而不看结果** —— 模型常先写一版被 H1 拒、读到回执后改对。⇒ 改为取**最后一次 result 为成功**的那版。
3. **字段名不符** —— NDJSON 是平铺 `{type:'tool_call', tool, input}`，会话日志是嵌套 `{type:'tool/call', data:{name, arguments}}`，结果里的 callId 藏在 `data.message.toolCallId`。⇒ 统一用 `flat(x)` 兼容。

所以第二轮改为**直接读落盘文件**：`CALENDAR.md`、`event-store.json`、日志 `.md`、账本 `.md`、`PLAN.md`。工具入参对但没落盘，等于没记住。

### 1.3 安全隔离（四层，实测有效）

| 层 | 手段 | 实测 |
|---|---|---|
| 记忆库隔离 | 独立 `DSH_HOME` + 显式覆盖 `memoryRoot`/`userMemoryDir` | 真实库 **1,231 个工作区，实验期间零变化** |
| 文件系统沙箱 | `DSH_PERMISSION_MODE=workspace-write` | 越界写被拒（`[sandbox: file access denied]`） |
| 升级路径封死 | headless 无审批通道 | `danger-full-access` → `requires approval, but no approval channel` → **失败关闭** |
| 完整性哨兵 | 每次任务前后全量 sha256（5,379 真实文件 + 664 产品文件 + 27 提示词层） | **约 120 次检查，违规 0** |

**沙箱三要素**（缺一个就整条跑不起来，都实测过）：
1. `DSH_PERMISSION_MODE=workspace-write`
2. `TEMP`/`TMP` 指到可写目录 —— `writableRoots` 含 `tmpdir()`，提权后 `TEMP` 变成 `C:\Windows\System32`，该目录受 TrustedInstaller 保护 ⇒ `grantWrite()` 必然 `Win32 error 5`
3. 目录 ACL 含 `WRITE_DAC` + `WRITE_OWNER` —— 提权脚本一次性授予

### 4.4 为什么改提示词没用

试过三个方向，都不管用：

- **R1 把 create 挪到第 2 步之前 + 三路分支** —— 只在 `empty` 世界有效（本来就是那条路）；`hasEvent` 世界仍然 0/2。
- **R2/R3 给「选事件」的完整判据**（只留 active / 7 天内 / updatedAt 最新 / 排除 closed）—— 判据本身对，但**模型根本没走到那一步**，它在 `memory_recall` 就卡住了。
- **R3 明确 revision 的取法**（取最外层那一个 + 冲突重试 1 次）—— 同样是下游问题。

⇒ **瓶颈不在措辞，在 `memory_recall(scope=events)` 的检索方式**。

### 4.5 修法建议（需要改代码，本轮未实施）

**最小改动**：给接续仪式增加一个**不需要关键词**的入口——直接列当前工作区的活跃事件。

```
memory_recall(scope="events", query="")   # 空 query ⇒ 列出全部 active 事件（id + name + updatedAt）
```

或者新增一个 `memory_event(action="list", status="active")`。仪式的第 0 步改用它，**零猜测**。

**为什么这是正解**：仪式要的是「我这个会话属于哪个事件」，这是个**枚举题**，不是检索题。用关键词检索去解枚举题，必然靠猜。

**次优改动**（不改工具面）：让 `memory_recall(scope=events)` 在 `query` 为空或 `*` 时返回全部 active 事件列表。

## §5 最终推荐的提示词

基于实测，`snapshotSlimMaintain`（现 1,149 字符）可压到 **198 字符**，且**一次写对率从 0/5 提到 5/5**：

```
[记忆结构] 记忆以事件为中心。写记忆用 memory_* 工具。
交接账本用 memory_note(kind=handoff)，标题必须逐字为
## 任务状态 / ## 目标 / ## 已试方案与失败原因 / ## 进度与下一步。
★标题行只写这四个词，不要加任何后缀（不要写（type:state）这类标记，
type 标记只能写在标题下面的正文行）。每段至少 20 字符。
```

**但不要指望它省 token**（实测变化落在噪声内，无可测量收益）。收益在**减少往返**。

### 5.1 不该删的内容（有实测依据）

| 内容 | 位置 | 依据 |
|---|---|---|
| 「标题必须逐字」 | `snapshotSlimMaintain` | V1/V2/V4 一次写对全靠它；删了退回 19/20 需被拒 |
| 「不要加后缀」 | 同上 | `abl_polluted` 证明这是最常见的污染形态 |
| 四类感知的触发条件与字段形状 | `renderMemoryStatic`（硬编码 6,220 字符） | 第二轮 15/15 全靠它；**且它是唯一来源**（`injectEnabled:false` 时模型仍知道，说明来自 schema + 静态段） |
| 日历的「主动记 deadline」 | 同上 | `cal-relative` 正确把「明天」换算成 2026-10-30 |

### 5.2 明确不要做的事

| 不做 | 依据 |
|---|---|
| 指望精简提示词省 token | 实测 1,149→45 字符，token 变化落在噪声内（同配置三次分布 2,439–2,958） |
| 给合规率设「95% 目标」 | 天花板已是 100%（约 120 次调用全部通过） |
| 用「LLM 自评」替代判据门 | `abl_polluted` 证明判据门能拦住的，指令层面拦不住 |
| 为「四类感知质量」加硬判据 | 模型现在写得对，硬加判据会像 `abl_polluted` 一样把正常路径堵死 |
| 在 headless 环境测「工具描述改写」 | description 硬编码在 `defineTool()` 里，改就是改产品代码 |

## §6 发现的产品缺陷清单（按严重度）

| # | 缺陷 | 证据 | 建议 |
|---|---|---|---|
| **D1** | **`memory_recall(scope=events)` 用于接续仪式必然靠猜** | `hasEvent` 世界完成率 15%（13 次里 11 次超时）；空库 92% | 给仪式提供「列出 active 事件」的零猜测入口 |
| **D2** | **一个坏事件毒死整个事件库的写入** | `missing:skillRef,bad-kind:task` 挡住 3 次连续 create；错误不指明是哪个事件 | 错误信息区分「本次入参」vs「库存存量」；坏事件降级为跳过而非全局 fail |
| **D3** | **四类感知只校验 `stage` 一个字段** | 审计：`text`/`kind`/`action`/`claim`/`promise`/`state` 全不校验 | 至少给 `text`/`claim`/`promise` 加非空校验（软警示即可，别硬拒） |
| **D4** | **`calendar_add` 的 date/time 完全不校验** | 任意字符串都收 | 加日期格式软校验 + 不合理日期提示 |
| **D5** | **`renderMemoryStatic()` 硬编码不可配置** | `promptLayerOverrides` 改不到它 | 至少拆出「四类感知」和「日历」两节给配置层 |
| **D6** | 模型在拿不到上下文时会翻整个文件系统 | 一次 41 个工具调用，读到实验脚手架 | 沙箱默认禁止 `-Recurse` 到工作区外；或在系统提示里明确「不要递归搜索」 |

D1 和 D2 建议优先处理——它们直接导致「仪式做不成」和「事件库写不进」。

## §10 对原方案价值主张的最终判断

原方案主张：**省 1,498 字符 + 提高合规率**。

| 主张 | 实测 | 判定 |
|---|---|---|
| 省字符 | 提示词可压 1,149→198（省 951 字符/请求） | ✅ 成立 |
| 省 token | 实测删 1,104 字符后 token 变化**落在采样噪声内**（同配置三次 2,439–2,958） | ❌ 不成立 |
| 提高合规率 | 天花板已是 100%，无空间 | ❌ 不成立 |
| 回执承载指导 | `abl_distrust` 证明回执权重 > 指令 | ✅ **成立且比原以为更强** |
| 四类感知需要新建校验 | 模型现在写得对，且注入全关也对 | ⚠️ **不紧急**（但 D3/D4 是真空缺） |

**修正后的价值主张**：

> 把约 950 字符的四段规则从提示词搬到**判据门回执**，收益不是省 token，而是**消除「先写错再改」的往返**（实测 5/5 → 0/5），并让指导落在一个**模型会主动优先信任**的通道里。
>
> 真正的产品优先级应该转向 **D1（接续仪式找不到事件）** 和 **D2（坏事件毒死写入）**——这两个是会让用户实际做不成事的缺陷，比提示词长短重要得多。
