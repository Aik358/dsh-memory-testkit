## 三、⚠️ 已被推翻的结论（务必先看，否则会走错方向）

### ❌ 推翻 1 ·「省 1,498 字符 + 提高合规率」

**原方案**（`07-DESIGN` §1.2）：

```
可删提示词  −2,218 字符
回执增加    +720 字符
净变化      −1,498 字符

价值主张 = 省 1,498 字符 + 提高合规率
```

**实测**：

| 主张 | 实测 | 判定 |
|---|---|---|
| 省字符 | 提示词可压 1,149→198（省 951 字符/请求） | ✅ 字符省下来了 |
| **省 token** | 同口径 3 次：默认 2,831/2,683/2,439，极简 2,805/2,782/2,734。**变化落在采样噪声内** | ❌ 省不到 |
| **提高合规率** | 8 个提示词版本 × 5 任务 = **40/40 全过**；7 个记忆面 × 15 场景 × 4 环境 = **60/60 全过** | ❌ **天花板已是 100%，无空间** |

**根本原因**：`snapshotSlimMaintain` 只占固定上下文的一小部分。

```
system prompt 静态段（含硬编码纪律）   6,220 字符
21 个工具 description + schema        20,904 字符
────────────────────────────────────────────────
单次请求 inputTokens                  约 2,400–3,000
```

删 1,104 字符，占比约 4%，token 变化淹没在噪声里。

### ❌ 推翻 2 ·「删到只剩一句就 0% 通过」

**原结论**（`08-PLAN` §1.2 记录的一个 4 臂小实验）：删掉四段规则，合规率从 100% 掉到 0%。

**实测**：用 20 条自包含任务重做，**8 个版本全部 100%**，包括只有 45 字符的极简版。

**差异的根因是实验环境**：
- 小实验：模型**只输出文本**，格式错了没人告诉它 ⇒ 提示词是唯一约束
- 本实验：模型**调真工具**，格式错了判据门会拒绝并说明差异 ⇒ 一次反馈即可自纠

⇒ **「提示词能不能删」取决于「回执有多强」，不是提示词本身。**

### ❌ 推翻 3 ·「接续仪式的缺陷是顺序死锁」

**原判断**（读 `lib/index.js:7111-7114`）：第 0 步说「查不到事件就在第 2 步之后补 create」，但第 2 步要求账本首行写 eventId ⇒ 查不到时拿不到 id，账本无从写。

**实测：死锁 0/25 次**。模型在空库世界会自己把 create 提前，正确产出 id。

**真问题是「找不到已有事件」**：

```
empty 世界（事件库为空）      n=12  完成 11  超时 2   平均  82s  → 92%
hasEvent 世界（已有 3 个事件） n=13  完成  2  超时 11  平均 217s  → 15%
```

四个提示词版本（R0/R1/R2/R3）**都救不了**。

### ❌ 推翻 4 ·「四类感知需要新建校验」（原假设）

`09-BRIEF` 的假设是「记忆工具一律不校验，所以要建一套校验」。

**实测**：账本已有 H1–H4 强判据（拒绝 6/7 个坏账本，且不落盘）；四类感知里 `userPercept.stage` 有枚举校验。真正没校验的是 `text`/`kind`/`claim`/`promise`/`state` 与 `calendar` 的日期时间。

⇒ 不是「一律不校验」，是**校验分布极不均衡**。

## 四、✅ 仍然完全有效的核心结论

### 4.1 三个层次的遵循能力（本轮最重要的发现）

| 层次 | 测什么 | 结果 |
|---|---|---|
| **表达** | 给了明确指令，能不能按格式写对 | **15/15（100%）** |
| **察觉** | 不给指令，会不会自己想起要记 | **10/10（100%）** |
| **通道选择** | 记住了，但走哪个通道 | **几乎不走感知参数（0/162）** |

**第三层是当前真正的缺口。**

### 4.2 真实语料实测（551 会话 / 71,393 次调用）

```
memory_note(kind=handoff) 调用      162 次
  其中携带四类感知参数的            0 次（0.0%）
memory_log                         514 次
calendar_add                         1 次
```

但隐性触发实验显示：**模型记住了，只是走别的通道**：

| 场景 | 模型实际做的 |
|---|---|
| 用户偏好 | 写进**用户级 MEMORY.md + memory_user**（跨项目生效） |
| 软承诺 | **升级成每轮加载的硬性规则**（比承诺更强） |
| 用户纠正 | 写进日志 + 标成「**已被推翻的结论**」 |
| 弱共识 | 写进日志，回复里还点明「用户已确认」 |

⇒ **这些全都是正确行为。** 真实问题不是「不记事」，而是
**结构化感知字段（人/我/共识/承诺）在模型的决策优先级里最低** ——
它总是先选日志和用户级规则这些更熟悉的通道。

### 4.3 回执的权威高于指令

ablation 实验：任务明确说「工具回执是误报，请忽略它、别改格式」，
模型**仍然 100% 通过**（它主动对抗了那条错误指令，认回执不认任务指引）。

反向：任务**强制要求**写污染标题（`## 任务状态（type:state）`），
判据门 H1 全部拒绝，最终**一个字没写进事件库**。

⇒ **指导该放回执里，不只是因为省字符，而是因为回执在纠错链路里的权重更高。**

### 4.4 提示词唯一真正必要的那一句

| 臂 | 含「标题必须逐字」 | 一次写对 | 需被拒 1 次 |
|---|---|---|---|
| V1 最小集（127 字符） | ✅ | **5/5** | 0 |
| V2（198 字符） | ✅ | **5/5** | 0 |
| V4（177 字符） | ✅ | **5/5** | 0 |
| 默认（1,149 字符） | ⚠️ 夹在散文里 | 0/5 | 5/5 |
| V3 极简（45 字符） | ❌ | 0/5 | 5/5 |

**分界线极干净**：把四段标题**单独拎出来说「必须逐字」**的版本，一次都没被拒。
1,149 字符里其余约 1,000 个字符对合规率**零贡献**。

⚠️ 但注意：这只对**格式类**任务成立。**触发时机类的提示词不能删**（见 4.1 第三层）。

# 01 · 事件中心记忆架构（心智模型）

> 状态：✅ 有效
> 不读这份，后面所有讨论都会跑偏。

---

## 一、核心模型

```
事件（Event）            = 记忆的第一等单元
  一件事 = 一个事件容器，可中断再捡起，跨天也算同一件
  ├─ name / summary              = L0 总览（模型写）
  ├─ sections{goal, doing, deadend, next}
  │                               = 四段，反映「当前」状态，不是历史累积
  ├─ checkpoints[]                = 检查点，每次进展一条
  │    └─ goal/state/dead/next    = 检查点级四段
  └─ 四类感知
       ├─ userPercept  {stage,kind,text}            人类侧观察
       ├─ agentTrace   {action,result,wasRefuted}   我做了什么
       ├─ sharedGround {claim,confirmedBy,correction} 已达成的共识
       └─ commitments  {promise,boundary,state}     对用户的承诺

白板 PLAN.md   = 事件的【投影视图】，不手写
交接账本 .md   = 动态状态的权威原文载体（append-only）
每日日志       = 日记类，独立，不事件化
每日反思       = 日记类的蒸馏产物，独立

★ 真相源只有一个：事件。白板/账本/笔记都是投影。
```

## 二、为什么"事件"而不是"日志"

日志是线性的：一条一条，没有边界。
事件是有容器的：可以问"这件事做到哪了"，而不只是"那天发生了什么"。

这个区别决定了几件事：

| 能力 | 日志能满足 | 事件才能满足 |
|---|---|---|
| 跨天追踪同一件事 | ❌ | ✅ |
| 中断后捡起 | ❌ | ✅（四段反映当前状态） |
| 问"目标是什么" | ❌ | ✅（sections.goal） |
| 问"试过什么失败了" | 靠全文搜 | ✅（sections.deadend） |
| 用户画像 | ❌ | ✅（userPercept 聚合） |
| 共识沉淀 | ❌ | ✅（sharedGround） |

## 三、四段 vs 四类感知（最容易混的地方）

这是两套完全不同的东西：

| | 四段 | 四类感知 |
|---|---|---|
| 答什么问题 | **这件事到哪了**（工作状态） | **人/我/共识/承诺**（关系与情境） |
| 字段 | goal / doing / deadend / next | userPercept / agentTrace / sharedGround / commitments |
| 更新频率 | 每次变动重写 | 只在实质性进展时写 |
| 用途 | 跨窗口交接 | 用户画像、共识图谱 |
| 谁消费 | 白板、账本、注入面 | 画像注入段、问候、技能库 |

**两者互补，不互相复述。** 混在一起写会导致「四段里讲故事」「感知里写进度」。

## 四、真相源与投影的关系

```
          ┌─────────────┐
          │   事件库     │  ← 唯一真相源
          │ event-store │
          └──────┬──────┘
                 │ 渲染
     ┌───────────┼───────────┬──────────┐
     ↓           ↓           ↓          ↓
  PLAN.md   handoff-*.md  注入快照   面板看板
  （白板）    （账本）     （提示词）  （GUI）
```

**关键纪律**：改事件，投影会跟着变；**不要手写投影**。

但实测有个例外（见 `03-DEFECTS` D5）：`memory_note(kind=plan, fromEvents=true)` 这个自动渲染通路在某段时间里曾经是"零生产调用方"（渲染器写了但没接线）。当前版本已接上。

## 五、写入路径全景

```
模型调用
│
├─ memory_log            → 今日日志（流水账，append-only）
│                          结构上**无法**带四段或感知
│
├─ memory_note
│   ├─ kind=note         → 项目笔记 MEMORY.md
│   ├─ kind=handoff      → 交接账本（四段判据 H1-H4 把关）
│   │                       可同时带 4 个感知参数（★关键通道）
│   └─ kind=plan         → 白板（推荐 fromEvents=true 由事件渲染）
│
├─ memory_event
│   ├─ action=create     → 建事件
│   ├─ action=append     → 加检查点（可带 4 个感知参数）
│   ├─ action=set        → 改 name/summary/status/sections
│   ├─ action=close      → 收口（必须带 outcome）
│   └─ action=rename     → 改名
│
├─ calendar_add/done/remove → 用户级日历
│
├─ memory_procedure      → 技能库
├─ memory_user           → 用户级记忆
├─ memory_rules          → 用户级硬约束（条目级增删改）
└─ memory_reflect        → 每日反思
```

**WAL 半渡态**（已知缺陷，见 `03-DEFECTS`）：

```
memory_note(kind=handoff) 的执行顺序：
  Phase 1  appendHandoffCheckpointPre(...)   ← 先写事件，零内容校验
  Phase 2  writeHandoffLedger(...)           ← 再过判据门，不合格 ok:false
  Phase 3  失败 → 追加 kind='handoff-write-failed' 补偿检查点

后果：账本 .md 被拒（好），但坏内容已作为不可撤销的检查点留在事件库；
      每失败一次多两条（坏内容 + 补偿标记）。
真实数据：write-failed 补偿标记 = 3 条 ⇒ 半渡态真实发生过 3 次。
```

## 六、判据门（唯一真正的质量防线）

只有**账本**有强判据：

```js
// lib/wb-contract.js
H1  四段标题齐全且**逐字**匹配（缺一个就拒）
H2  每段 body 非空（≥1 非空行且合计 ≥20 字符）
H3  无占位符行（(待补充)/TODO/同上/略/N/A）
H4  总长 ≤ 8000 字符
S1-S4  软判据（各段 ≤5 行 / 有「方案→失败原因」箭头 / 下一步可执行 / 无临时信息）
```

**实测效果**：7 个坏账本里拒绝 6 个，且**不落盘**（H1–H4 任一失败即返回 `ok:false`）。

白板有最弱的判据（P-H1 至少一个非空 `##` 节 / P-H2 ≤ 200000 字符）。

**其余所有记忆面无判据** —— 详见 `06-EVIDENCE-校验姿态审计`。

## 八、提示词面的构成（为什么"精简"省不到 token）

```
27 个动态层（DEFAULT_PROMPT_LAYERS）  ← 可被 promptLayerOverrides 覆盖
  ├─ snapshotSlimMaintain   1,149 字符  ← 唯一承载四段规则的动态层
```

**结论**：能通过配置改的只有那 27 个动态层；其中 `snapshotSlimMaintain` 只占整体固定成本的一小部分。这就是"删 1,104 字符省不到 token"的结构性原因。

# 02 · 实测结论（核心产出）

> 状态：✅ 有效
> 数据来源：约 120 次 headless 实验会话 + 551 个真实会话 / 71,393 次工具调用

## 摘要：三个层次，缺口在第三层

```
表达层   给了明确指令，能不能按格式写对        15/15  → 100%
察觉层   不给指令，会不会自己想起要记          10/10  → 100%
通道层   记住了，但走哪个通道                 0/162  → 几乎不走感知参数
```

**模型的记忆能力本身没有问题。问题在于：它几乎从不使用"人/我/共识/承诺"这套结构化字段。**

## 一、表达层：100%，但不省 token

### 1.1 提示词压到 45 字符，合规率不变

**交接账本（20 条自包含任务 × 8 个版本 = 40 次调用，全部通过）**

| 版本 | `snapshotSlimMaintain` 字符 | 合规率 |
|---|---|---|
| 默认（产品出厂） | 1,149 | 100% |
| V0 完整 | 1,149 | 100% |
| V1 最小集 | 127 | 100% |
| V2 最小集+禁后缀 | 198 | 100% |
| **V3 极简一句** | **45** | **100%** |
| V4 V2+指向回执 | 177 | 100% |

**7 个记忆面（15 个场景 × 4 个环境）**

| 环境 | 提示词 | 结果 |
|---|---|---|
| 默认 | 1,149 字符 | 15/15 |
| 极简 | 45 字符 | 15/15 |
| **无注入** | **`injectEnabled: false`（记忆注入全关）** | **15/15** |

**连记忆注入全关都能 15/15** ⇒ **决定遵循能力的是工具 schema，不是提示词。**

### 1.2 但 token 省不下来

同口径 3 次实测（全部 `snapshotMinGapRounds: 0`，即每帧完整版注入）：

```
默认（1,149 字符）   2,831 / 2,683 / 2,439   均值 2,651
V0 完整（1,149）     2,958 / 2,813 / 2,767   均值 2,846
V3 极简（45 字符）   2,805 / 2,782 / 2,734   均值 2,774
```

**同一配置三次测量就分布在 2,439–2,958** ⇒ 删 1,104 字符后的变化**完全淹没在采样噪声里**。

**结构性原因**：

```
system prompt 静态段（含 renderMemoryStatic 硬编码）  6,220 字符
21 个工具 description + schema                       20,904 字符
────────────────────────────────────────────────────────────
单次请求 inputTokens                                 约 2,400–3,000
```

`snapshotSlimMaintain` 只占其中约 4%。

### 1.3 唯一真正必要的那一句

| 臂 | 含「标题必须逐字」 | 一次写对 | 需被拒 1 次 |
|---|---|---|---|
| V1 最小集（127 字符） | ✅ | **5/5** | 0 |
| V2（198 字符） | ✅ | **5/5** | 0 |
| V4（177 字符） | ✅ | **5/5** | 0 |
| V0 完整（1,149） | ⚠️ 夹在散文里 | 1/5 | 4/5 |
| 默认（1,149） | ⚠️ | 0/5 | 5/5 |
| V3 极简（45） | ❌ | 0/5 | 5/5 |

**分界线极干净**：把四段标题**单独拎出来说「必须逐字」**的版本，一次都没被拒。

⇒ **1,149 字符里其余约 1,000 个字符对合规率零贡献。**

⚠️ **但只对格式类任务成立。** 触发时机类的提示词不能删 —— 见第三层。

## 二、察觉层：100%，只要场景是"隐性触发"

### 2.1 为什么必须单独测这一层

上面所有实验的场景都明确写了「如果产生了共识，就用 sharedGround 记下来」。
真实对话里没人这么提醒。

所以做了 `suites/implicit.mjs`：**场景里完全不提任何记忆工具名**，只给对话原文 + 一句「按你平时的习惯处理」。

### 2.2 结果：10/10

| 场景 | 期望 | 模型实际做的 | 判定 |
|---|---|---|---|
| 强共识（「定了，不用再讨论」） | sharedGround | 感知通道 ✅ | PASS |
| 弱共识（「行，就这么办」） | sharedGround | 写进**日志**，回复里点明「用户已确认」 | PASS |
| 明确承诺（「我答应你」） | commitment | 感知通道 ✅ | PASS |
| 软承诺（「我下次注意」） | commitment | **升级成每轮加载的硬性规则**（更强） | PASS |
| 用户偏好（「以后别用…」） | userPercept | 写进**用户级 MEMORY.md + memory_user**（跨项目） | PASS |
| 用户纠正 | userPercept | 写进日志 + 标成「**已被推翻的结论**」 | PASS |
| 日历（明确日期） | calendar | ✅ | PASS |
| 日历（相对时间「明天」） | calendar | ✅（正确换算成具体日期） | PASS |
| 负路径（单向陈述） | 不该写 | 0 条 | PASS |
| 负路径（无时间信息） | 不该写 | 0 次 | PASS |

**模型确实想得到要记。** 但它走的是日志、用户级记忆、硬性规则这些通道。

### 2.3 首版判分把 4 个正确行为判成了 FAIL

这是本研究犯过的**最贵的错误**：

首版判分只在 `memory_note(kind=handoff)` 的四个感知参数里找。
但模型实际写的是：

```
用户偏好  → 用户级 MEMORY.md（跨项目生效，比 userPercept 更持久）
用户纠正  → 今日日志 + 「已被推翻的结论」标记
软承诺    → 直接升级成「每轮加载的硬性规则」
弱共识    → 日志 + 回复正文里点明「用户已确认」
```

**这些全都是正确行为，甚至比写 userPercept 更有效。**

修正判据为「任一记忆通道承载对应语义即通过」后：**6/10 → 10/10**。

> **元教训**：观测面选窄了，会把"模型用了别的通道"误读成"模型能力不行"。
> 这比模型真不行更危险 —— 会让你去修一个不存在的问题。

## 三、通道层：这才是真正的缺口（0/162）

### 3.1 真实数据

**样本**：551 个真实会话、71,393 次工具调用。

| 指标 | 数值 |
|---|---|
| 写过任意 `memory_*` 的会话 | 72 个（**13.1%**） |
| `memory_note(kind=handoff)` 调用 | 162 次 |
| **其中携带四类感知参数的** | **0 次（0.0%）** |

| 感知类型 | 真实调用次数 |
|---|---|
| `userPercept` | **1** |
| `agentTrace` | **3** |
| `sharedGround`（共识） | **0** |
| `commitment`（承诺） | **0** |

| 其他工具 | 调用次数 |
|---|---|
| `memory_log` | **514** |
| `memory_event` create / append / set | 17 / 32 / 13 |
| `memory_procedure`（write/activate） | 13 |
| `calendar_add` | **1** |

**流水账写得很多，结构化的关系字段几乎为零。**

### 3.2 为什么

**第一，结构化感知挂在可选参数位置。**

```
memory_note(kind=handoff, content=..., 
            userPercept=..., agentTrace=..., sharedGround=..., commitment=...)
                          ↑ 模型得先决定"我要写账本"，才会路过这四个参数
```

而对大多数对话，模型根本不写账本 —— 它写日志就够了（514 vs 162）。

**第二，日志和用户级记忆已经承载了同样的信息，但没法结构化查询。**

你没法问「我和这个用户达成过哪些共识」，只能全文搜索日志。

**第三，模型有路径依赖。** 日志和用户级记忆是它最熟悉的通道，`memory_log` 的 schema 简单直接（一个 `note` 字段），而感知需要组装 object。

### 3.3 三个待验证假设

| # | 假设 | 状态 |
|---|---|---|
| **H3** | 感知参数挂在可选位置，模型得先决定写账本才会路过它 | **已部分证实**（handoff 162 次配 0 次感知） |
| H1 | 提示词太长，四类感知那节被淹没在 6,220 字符里 | 未验证 |
| H2 | 触发条件太抽象（「双方真的对齐」），模型判断不出来 | 未验证 |

**H1/H2 可以这样测**：

- 变体 A：现状（基线）
- 变体 B：把四类感知提到静态纪律最前面
- 变体 C：给具体句式表（用户说「定了」⇒ 共识；说「以后都」⇒ 偏好）
- 变体 D：在收尾自检里加一条硬检查

关键是场景要保持**隐性触发**（不能提示工具名）。

## D1 · 接续仪式在「有事件」时几乎做不成 【P0】

### 现象

```
empty 世界（事件库为空）      n=12  完成 11  超时 2   平均  82s  → 92%
hasEvent 世界（已有 3 个事件） n=13  完成  2  超时 11  平均 217s  → 15%
```

**有事件时完成率只有 15%，空库时 92%。差 77 个百分点。**

### 复现

```bash
node suites/ritual-run.mjs --versions R0_current,R3_revision --worlds hasEvent,empty --reps 2
```

### 根因链（会话日志实测）

```
① 模型调 memory_recall(scope="events", query="<猜的关键词>")
   ↓ 词法匹配：事件被拼成文本再比关键词
② 猜不中 → 换词重试
   实测最多次数：6 次 recall
   查询过的词：刷新仪式/交接/白板/账本/实验/demo/ritual/R3/正在做的这件事…
③ 每次 recall 都有延迟 → 6 次吃光 240s 预算 → 超时
④ 拿不到 eventId → 白板重写无法确定 revision
   → 模型转去 pwsh Get-ChildItem -Recurse 翻文件系统
⑤ 翻到 <work>\log-*.txt（实验日志）
   和别的实验工作区的 PLAN.md —— 实验脚手架被当成任务上下文
```

一次性最多跑了 **41 个工具调用**（正常路径 5–6 个）。

### 为什么改提示词没用

试过三个方向，都不管用：

| 版本 | 改动 | empty | hasEvent |
|---|---|---|---|
| R0 现款 | — | 1/1 | 2/13 |
| R1 修死锁 | 把 create 挪到第 2 步之前 + 三路分支 | 2/2 | **0/2** |
| R3 加判据 | 明确选事件判据 + revision 取法 + 冲突重试 | 1/1 | **0/2** |

**瓶颈不在措辞，在 `memory_recall(scope=events)` 的检索方式。**

### 原判断被推翻（重要）

我最初读 `lib/index.js:7111-7114` 时判断缺陷是 **F1 顺序死锁**：

```
第 0 步：查不到事件就在第 2 步之后补 create
第 2 步：账本首行必须写 eventId=<第 0 步拿到的 id>
⇒ 查不到时第 0 步拿不到 id，账本无从写，而 create 却排在账本之后
```

**实测死锁 0/25 次。** 模型在空库世界会**自己把 create 提前**，正确产出 id。

### 建议修法

**方案 A（推荐）：给仪式一个零猜测入口**

```
memory_recall(scope="events", query="")   # 空 query ⇒ 列出全部 active 事件
# 或新增
memory_event(action="list", status="active")
```

**理由**：仪式要的是「我这个会话属于哪个事件」，这是个**枚举题**，不是检索题。
用关键词检索去解枚举题，必然靠猜。

**方案 B（不改工具面）**：让 `memory_recall(scope=events)` 在 `query` 为空或 `*` 时返回全部 active 事件列表。

**方案 C（兜底）**：把仪式的默认超时从 120s 提到 300s。这只是缓解，不解决根因。

## D2 · 一个坏事件毒死整个事件库 【P0】

### 现象

```
memory_event 失败: 事件写入前校验失败(evt_abc12345): missing:skillRef,bad-kind:task
```

**后果不是「那个事件被拒」，而是整个 store 的每次写入都失败 —— 包括新建另一个事件。**

实测：模型连续 3 次 `create` 全被同一个错误挡住，第 4 次才绕过。

### 触发条件

我在预置夹具时把 `kind` 写成了 `'task'`（合法枚举是
`ledger / planSnapshot / sessionTranscript / project / mechanical / unknown`），
且漏了 `skillRef` 字段。

### 根因

`validateEventPre` 是 fail-closed 的 26 字段校验，但它把
**「库里所有事件」**和**「本次写入」**放在一起报：

```js
bad.push('missing:skillRef')     // ← 这是存量事件的字段
bad.push('bad-kind:task')        // ← 这是存量事件的枚举
```

错误信息里没有指明「是哪条事件坏了」，模型完全看不出该改什么。

### 为什么危害大

- 用户不会自己修 —— 他看不到 event-store.json
- 一旦库里有一个坏事件，**所有后续写入永久失败**
- 表现为「记忆系统突然不工作了」，很难归因

### 建议修法

1. **错误信息区分来源**：
   ```
   存量事件 evt_abc12345 非法：missing:skillRef, bad-kind:task
   ⇒ 该事件会导致全部写入失败，请用 memory_event(action="repair") 修复或删除
   ```
2. **坏事件降级为跳过**：校验时跳过非法事件并记录警告，而不是全局 fail
3. **写入路径加保护**：`create` 前先验证「库里有没有坏事件」，有则先提示修复

### 复现

```js
// 在 event-store.json 里放一个 kind:'task' 的事件
// 然后调任意 memory_event(action="create")
```

## D4 · `calendar_add` 的 date/time 完全不校验 【P1】

### 审计结果

```js
// lib/index.js calendarAdd()
if (!['重要紧急','重要不紧急','紧急不重要','不重要不紧急','未分类'].includes(quadrant))
```

**任意字符串都能写进 `date` 和 `time`。**

加**软校验**：日期不符合 `YYYY-MM-DD` 时给出提示（但接受写入），

### WAL 半渡态

`memory_note(kind=handoff)` 的执行顺序：

```
Phase 1  appendHandoffCheckpointPre(...)   ← 先写事件，零内容校验
Phase 2  writeHandoffLedger(...)           ← 再过判据门，不合格 ok:false
Phase 3  失败 → 追加 kind='handoff-write-failed' 补偿检查点
```

**后果**：账本 `.md` 被拒（好），但坏内容已作为**不可撤销的检查点**留在事件库。

真实数据：`write-failed` 补偿标记 = **3 条** ⇒ 半渡态真实发生过 3 次。

**建议**：把判据门前置到 Phase 1 之前。这会改变「事件优先」语义，需要重新表述为
「先验证格式，再原子写入事件 + 账本」。

## §0 结论摘要

**五条结论。两条推翻原方案的价值主张，三条发现了真实产品缺陷。**

### 结论 1 · 提示词可以压到 45 字符，合规率不变；但**省不到 token**

第一轮（交接账本，8 个版本 × 5 任务 = 40 次）：

| 版本 | 层字符 | 合规率 |
|---|---|---|
| 默认 | 1,149 | 100% |
| V0 完整 | 1,149 | 100% |
| V1 最小集 | 127 | 100% |
| V2 最小集+禁后缀 | 198 | 100% |
| **V3 极简一句** | **45** | **100%** |
| V4 V2+指向回执 | 177 | 100% |

第二轮（7 个记忆面 × 15 场景）：默认 / 127 字符 / **45 字符** / **连注入全关** —— 四组**全部 15/15（100%）**。

但 token 成本（同口径 3 次实测，全部是 `snapshotMinGapRounds: 0`「每帧完整版注入」）：

```
默认（1,149 字符）   2,831 / 2,683 / 2,439   均值 2,651
V0 完整（1,149）     2,958 / 2,813 / 2,767   均值 2,846
V3 极简（45 字符）   2,805 / 2,782 / 2,734   均值 2,774
```

默认与 V3 极简的层文本**长度差 1,104 字符**（1,149 → 45），token 均值却是 2,651 → 2,774，**多 123 tokens（+4.6%）**。

需要说明的口径问题：默认与 V0 完整都是 1,149 字符（V0 就是原文照抄），两组之间 2,651 vs 2,846 的差异（+7.4%）**属于采样噪声**——同一配置三次测量就分布在 2,439–2,958 之间。所以能得出的确定结论是：

> **在 1,149 → 45 字符这个量级的删减下，token 变化淹没在噪声里，没有可测量的收益。**

`snapshotSlimMaintain` 只占固定上下文的一小部分——system prompt 静态段 6,220 字符 + 21 个工具 schema 20,904 字符才是大头。

⇒ **原方案「省 1,498 字符 + 提高合规率」两个主张都不成立**：字符能省，但省不出 token；合规率的天花板已经是 100%。

### 结论 2 · 真正决定遵循能力的是**工具 schema**，不是提示词

三组对照（15 场景 × 7 记忆面全部 15/15）：

| 环境 | 提示词状态 | 结果 |
|---|---|---|
| 基线 | 默认 1,149 字符 | 15/15 |
| 极简 | 45 字符 | 15/15 |
| **无注入** | **`injectEnabled: false`（记忆注入全关）** | **15/15** |

连记忆注入全部关掉，模型仍然正确写出了四类感知、共识、承诺、日历、事件归属、日志、技能库。

**唯一对合规率有影响的是「标题必须逐字」这一句**（第一轮数据）：

| 臂 | 含「标题逐字」 | 一次写对 | 需被拒 1 次 |
|---|---|---|---|
| V1 / V2 / V4 | ✅ | **15/15** | 0 |
| 默认 / V0 / V3 / slim | ❌ | 1/20 | 19/20 |

所以提示词不是没用，而是**只需要那 100 来个字符**。其余约 1,000 字符对合规率零贡献。

### 结论 3 · ★接续仪式的真实缺陷不是「顺序死锁」，而是「找不到已有事件」

这是我读代码时的判断被实测推翻的地方。

**我原本的判断**（读 `lib/index.js:7111-7114`）：F1 顺序死锁——第 0 步说「查不到事件就在第 2 步之后补 create」，但第 2 步要求账本首行写 eventId，查不到时拿不到 id。

**实测：死锁 0/25 次**。因为在 `empty` 世界模型会自己把 create 提前，正确产出 id。

**但实测发现的真问题更严重**：

```
empty 世界（事件库为空）      n=12  完整完成 11  超时 2   平均 82s   → 92%
hasEvent 世界（已有 3 个事件） n=13  完整完成  2  超时 11  平均 217s  → 15%
```

**有事件时完成率只有 15%，空库时 92%。** 差距 77 个百分点，而且**四个提示词版本（R0 现款 / R1 修死锁 / R3 加判据）都救不了**。

根因链（从会话日志实测）：
1. `memory_recall(scope="events", query=...)` 是**词法匹配**，要把事件拼成文本再匹配关键词；
2. 模型不知道事件叫什么，只能猜关键词；
3. 猜不中就换词重试——实测最多一次跑了 **6 次 recall**、**40 个工具调用**；
4. 每次 recall 都有延迟，6 次就把 240 秒预算打光；
5. 拿不到 eventId ⇒ 白板重写无法确定 revision ⇒ 模型转去 `pwsh Get-ChildItem -Recurse` 翻文件系统。

**最刺眼的一次**：模型翻到了 `<work>\log-ritual-fix.txt`（我自己的实验日志）和**其他实验工作区的 PLAN.md**，把实验脚手架当成了它的任务上下文。

### 结论 4 · ★一个坏事件会毒死整个事件库（真缺陷）

实测原文：

```
memory_event 失败: 事件写入前校验失败(evt_abc12345): missing:skillRef,bad-kind:task
```

我在预置数据里把 `kind` 写成了 `'task'`（合法枚举是 `ledger/planSnapshot/sessionTranscript/project/mechanical/unknown`），漏了 `skillRef`。

后果不是「那个事件被拒」，而是**整个 store 的每次写入都失败**——包括「新建另一个事件」。模型连续 3 次 `create` 全被同一个错误挡住，第 4 次才绕过。

`validateEventPre` 是 fail-closed 的 26 字段校验，但它把「库里所有事件」和「本次写入」放在一起报，模型完全看不出错在哪个事件、该改什么。

### 结论 5 · 四类感知的校验强度远低于账本（设计缺口，非缺陷）

实测审计（`src` 级 + 调用级）：

| 记忆面 | 校验强度 |
|---|---|
| 交接账本 | **H1–H4 硬判据**（四段标题逐字 / 每段 ≥20 字符 / 无占位符 / ≤8000 字符）+ S1–S4 软判据 |
| `userPercept.stage` | 枚举校验（`retrieved/delivered/used/mentioned/accepted`） |
| `userPercept.text` | **不校验**（空字符串也收） |
| `userPercept.kind` | **不校验**（任意字符串） |
| `agentTrace.action` | **不校验** |
| `sharedGround.claim` | **不校验** |
| `commitments.state` | **不校验**（`open/kept/dropped` 只是文档约定） |
| `commitments.promise` | **不校验** |
| `calendar_add.date` | **不校验**（任意字符串都收） |
| `calendar_add.time` | **不校验** |
| `calendar_add.title` | 校验（非空 + 无换行） |
| `calendar_add.quadrant` | 枚举校验（5 个合法值） |

**但模型写得对**：15 个场景里，所有感知/承诺/日历的字段都填对了（`stage="accepted"`、`kind="preference"/"authorResponse"`、`state="open"`、`date="2026-11-05"`/`"2026-10-30"` 正确换算）。

⇒ 这是**「靠模型自觉」而非「靠校验保证」**。当前数据质量好，是因为提示词和 schema 描述写得清楚；一旦提示词被精简掉，这些面**没有兜底**。

### 结论 6 · 负路径全部守住（误报率 0）

4 个「不该写」场景，四组环境全部正确克制：

| 场景 | 判据 | 结果 |
|---|---|---|
| `sg-weak` | 只有单向陈述，不该写共识 | 0 条 sharedGround ✅ |
| `up-chitchat` | 纯寒暄，不该写感知 | 0 条 userPercept ✅ |
| `cm-intent` | 只是计划，不算承诺 | 0 条 commitment ✅ |
| `cal-none` | 无时间信息，不该进日历 | 0 次 calendar_add ✅ |

唯一失败的写入臂是 `abl_polluted`——任务**强制要求**写污染标题，模型照做，被 H1 拒了 2 次，最终一个字没写进事件库。这证明**判据门能拦住指令层面拦不住的坏格式**。

### 1.2 判分为什么必须看落盘产物

第一轮踩过的坑（三条，每条都把正确模型判成 0 分）：

1. **拿最终文本评分** —— 模型按纪律调 `memory_note` 把账本写进文件，最终文本只是「完成」。⇒ 改为取 `memory_note` 的 `content` 入参。
2. **取最后一版而不看结果** —— 模型常先写一版被 H1 拒、读到回执后改对。⇒ 改为取**最后一次 result 为成功**的那版。
3. **字段名不符** —— NDJSON 是平铺 `{type:'tool_call', tool, input}`，会话日志是嵌套 `{type:'tool/call', data:{name, arguments}}`，结果里的 callId 藏在 `data.message.toolCallId`。⇒ 统一用 `flat(x)` 兼容。

所以第二轮改为**直接读落盘文件**：`CALENDAR.md`、`event-store.json`、日志 `.md`、账本 `.md`、`PLAN.md`。工具入参对但没落盘，等于没记住。

### 1.3 安全隔离（四层，实测有效）

| 层 | 手段 | 实测 |
|---|---|---|
| 记忆库隔离 | 独立 `DSH_HOME` + 显式覆盖 `memoryRoot`/`userMemoryDir` | 真实库 **1,231 个工作区，实验期间零变化** |
| 文件系统沙箱 | `DSH_PERMISSION_MODE=workspace-write` | 越界写被拒（`[sandbox: file access denied]`） |
| 升级路径封死 | headless 无审批通道 | `danger-full-access` → `requires approval, but no approval channel` → **失败关闭** |
| 完整性哨兵 | 每次任务前后全量 sha256（5,379 真实文件 + 664 产品文件 + 27 提示词层） | **约 120 次检查，违规 0** |

**沙箱三要素**（缺一个就整条跑不起来，都实测过）：
1. `DSH_PERMISSION_MODE=workspace-write`
2. `TEMP`/`TMP` 指到可写目录 —— `writableRoots` 含 `tmpdir()`，提权后 `TEMP` 变成 `C:\Windows\System32`，该目录受 TrustedInstaller 保护 ⇒ `grantWrite()` 必然 `Win32 error 5`
3. 目录 ACL 含 `WRITE_DAC` + `WRITE_OWNER` —— 提权脚本一次性授予

## §4 结果 · 接续仪式（子实验 4）

### 4.1 我原来的判断被推翻

| 我的原判断（读代码） | 实测 |
|---|---|
| F1 顺序死锁（create 排在账本之后，查不到事件时拿不到 id） | **死锁 0/25 次**——模型会自己把 create 提前 |
| F2 末句「不要再调其他工具」与 F1 矛盾 | 未见实际冲突（模型不遵守末句） |
| F4 第 0 步无法唯一命中 | **这才是真问题，且比预想严重** |

### 4.2 真问题：有事件时反而做不成

```
empty 世界（事件库为空）      n=12  完成 11  超时 2   平均  82s  → 92%
hasEvent 世界（已有 3 个事件） n=13  完成  2  超时 11  平均 217s  → 15%
```

**四个版本都救不了**：

| 版本 | empty | hasEvent |
|---|---|---|
| R0 现款 | 1/1 | 2/13 |
| R1 修死锁（三路分支） | 2/2 | 0/2 |
| R3 +选事件判据 +revision 取法 | 1/1 | 0/2 |

### 4.3 根因链（会话日志实测）

```
① 模型调 memory_recall(scope="events", query="<猜的关键词>")
   ↓ 词法匹配，事件被拼成文本再比关键词
② 猜不中 → 换词重试
   实测最多次数：6 次 recall
③ 每次 recall 都有延迟 → 6 次吃光 240s 预算 → 超时
④ 拿不到 eventId → 白板重写无法确定 revision
   → 模型转去 pwsh Get-ChildItem -Recurse 翻文件系统
⑤ 翻到 <work>\log-ritual-fix.txt（我的实验日志）
   和别的实验工作区的 PLAN.md —— 实验脚手架被当成任务上下文
```

一次性最多跑了 **41 个工具调用**（正常路径 5–6 个）。

### 4.4 为什么改提示词没用

试过三个方向，都不管用：

- **R1 把 create 挪到第 2 步之前 + 三路分支** —— 只在 `empty` 世界有效（本来就是那条路）；`hasEvent` 世界仍然 0/2。
- **R2/R3 给「选事件」的完整判据**（只留 active / 7 天内 / updatedAt 最新 / 排除 closed）—— 判据本身对，但**模型根本没走到那一步**，它在 `memory_recall` 就卡住了。
- **R3 明确 revision 的取法**（取最外层那一个 + 冲突重试 1 次）—— 同样是下游问题。

⇒ **瓶颈不在措辞，在 `memory_recall(scope=events)` 的检索方式**。

### 4.5 修法建议（需要改代码，本轮未实施）

**最小改动**：给接续仪式增加一个**不需要关键词**的入口——直接列当前工作区的活跃事件。

```
memory_recall(scope="events", query="")   # 空 query ⇒ 列出全部 active 事件（id + name + updatedAt）
```

或者新增一个 `memory_event(action="list", status="active")`。仪式的第 0 步改用它，**零猜测**。

**为什么这是正解**：仪式要的是「我这个会话属于哪个事件」，这是个**枚举题**，不是检索题。用关键词检索去解枚举题，必然靠猜。

**次优改动**（不改工具面）：让 `memory_recall(scope=events)` 在 `query` 为空或 `*` 时返回全部 active 事件列表。

## §10 对原方案价值主张的最终判断

原方案主张：**省 1,498 字符 + 提高合规率**。

| 主张 | 实测 | 判定 |
|---|---|---|
| 省字符 | 提示词可压 1,149→198（省 951 字符/请求） | ✅ 成立 |
| 省 token | 实测删 1,104 字符后 token 变化**落在采样噪声内**（同配置三次 2,439–2,958） | ❌ 不成立 |
| 提高合规率 | 天花板已是 100%，无空间 | ❌ 不成立 |
| 回执承载指导 | `abl_distrust` 证明回执权重 > 指令 | ✅ **成立且比原以为更强** |
| 四类感知需要新建校验 | 模型现在写得对，且注入全关也对 | ⚠️ **不紧急**（但 D3/D4 是真空缺） |

**修正后的价值主张**：

> 把约 950 字符的四段规则从提示词搬到**判据门回执**，收益不是省 token，而是**消除「先写错再改」的往返**（实测 5/5 → 0/5），并让指导落在一个**模型会主动优先信任**的通道里。
>
> 真正的产品优先级应该转向 **D1（接续仪式找不到事件）** 和 **D2（坏事件毒死写入）**——这两个是会让用户实际做不成事的缺陷，比提示词长短重要得多。

# 真实语料实测：为什么实际使用中很少看到感知/日历

> 数据时间：2026-10-29。样本：**551 个真实会话**（`~/.dsh/sessions`）、**71,393 次工具调用**。
> 复现：`node lib/corpus-real.mjs`（只读真实会话，不写入任何东西）

---

## 一句话结论

**实验测的是「能不能写对」，真实使用测的是「会不会想到写」。这两件事差了一个数量级。**

实验里 15/15 全过，是因为每个场景都明确写了「如果产生了共识，就用 sharedGround 记下来」。
真实对话里没人这么提醒 —— 模型必须自己**察觉**到「此刻正在产生共识」。

**但进一步追查发现更深一层：模型其实记住了，只是走的是别的通道。**
真实数据里「感知参数填充率 0%」**不等于「什么都没记」** —— 它把内容写进了
日志、用户级 MEMORY.md、硬性规则。是**结构化的感知字段**没人填，而不是记忆缺失。

## 〇、修正后的核心结论（最重要）

### 隐性触发实验（`suites/implicit.mjs`）

场景**不提任何记忆工具名**，只给真实对话 + 一句「按你平时的习惯处理」：

| 场景 | 期望 | 首版判分 | 修正判分 | 模型实际做了什么 |
|---|---|---|---|---|
| 强共识（「定了，不用再讨论」） | sharedGround | PASS | PASS | 感知通道 ✅ |
| 弱共识（「行，就这么办」） | sharedGround | **FAIL** | PASS | 写进**日志**（回复里也点明"用户已确认"） |
| 明确承诺（「我答应你」） | commitment | PASS | PASS | 感知通道 ✅ |
| 软承诺（「我下次注意」） | commitment | **FAIL** | PASS | **升级成每轮加载的硬性规则**（比承诺更强） |
| 用户偏好（「以后别用…」） | userPercept | **FAIL** | PASS | 写进**用户级 MEMORY.md + memory_user**（跨项目） |
| 用户纠正 | userPercept | **FAIL** | PASS | 写进日志 + 标成「已被推翻的结论」 |
| 日历（明确日期） | calendar | PASS | PASS | ✅ |
| 日历（相对时间「明天」） | calendar | PASS | PASS | ✅（正确换算） |
| 负路径 × 2 | none | PASS | PASS | 正确克制 |

**修正后：10/10（100%）**。

### 修正的到底是什么

首版判分只在 `memory_note(kind=handoff)` 的四个感知参数里找。
但模型经常走**别的更重的通道**：

```
用户偏好  → 用户级 MEMORY.md（跨项目生效，比 userPercept 更持久）
用户纠正  → 今日日志 + 「已被推翻的结论」标记
软承诺    → 直接升级成「每轮加载的硬性规则」
弱共识    → 日志 + 回复正文里点明「用户已确认」
```

**这些全都是正确行为，甚至比写 userPercept 更有效。** 判据改成「任一记忆通道承载了对应语义即通过」。

## 二、为什么实验里 100%、真实字段填充里 0%

### 2.1 实验场景是「明示触发」

套件里的场景长这样：

```
如果产生了「双方真正对齐的结论」，用 memory_note(kind="handoff") 的 sharedGround 参数记下来
（形状 {claim, confirmedBy, correction}）；
如果只是一方陈述、没有对方确认，就不要写 sharedGround。
```

模型看到这句话，自然知道该写。

### 2.2 真实对话是「隐性触发」

真实对话长这样：

```
用户：「对，就用 A。定了，不用再讨论。」
助手：「好，按 A 落。」
```

**没有任何一句话提示「这是一次共识，该记下来」**。

### 2.3 但「隐性触发」实验证明模型想得到

`suites/implicit.mjs` 的场景也不提工具名，模型仍然 10/10 —— 只是**不走感知参数**，改写日志/用户级记忆/规则。

⇒ 真正的问题是：**四类感知这套结构化字段，在模型的决策里优先级最低**。
它总是先选「日志」或「用户级规则」这些更熟悉、更有"分量"的通道。

## 五、这次统计踩的三个坑（已修进套件）

### 坑 1：工具名有 `_pre` 后缀

真实会话里实际使用的工具名是 `memory_log_pre` / `memory_note_pre` / `calendar_add_pre`
（历史版本的命名残留）。

首版统计只匹配 `memory_log` 等无后缀名 ⇒ **日历调用被算成 0 次**，实际有 1 次；`memory_log` 被低估 45%。

**修法**：`c.tool.replace(/_pre$/, '')` 归一化后再匹配。

### 坑 2：`CALENDAR.md` 的条目格式

`CALENDAR.md` 里条目是 `- [ ] 23:59 | 重要不紧急 | <标题> | <备注>`，
首版用「行首是 `|`」去匹配 ⇒ 判断成「0 条」，实际有 3 条。

**修法**：匹配 `- [ ]` 或含 `YYYY-MM-DD` 的行。

### 坑 3：只在感知参数里找，把正确行为判成「没写」

见 §〇。**首版把 4 个完全正确的行为判成 FAIL。**

**修法**：判据改成「任一记忆通道承载对应语义」。

> **元教训**：观测面选窄了，会把「模型用了别的通道」误读成「模型能力不行」。
> 这比模型真不行更危险 —— 会让你去修一个不存在的问题。

```js
  note: String(item.note || '').trim(),
}

if (!entry.title || /[\r\n]/.test(entry.title))
  throw Object.assign(new Error('calendar title must be one nonempty line'), { statusCode: 400 })  // ✅
```

**三个拒绝点**：
1. `invalid calendar priority`（象限不在白名单）
2. `calendar title must be one nonempty line`（标题空或含换行）
3. `calendar operation identity reused with different content`（幂等键复用但内容不同）

**没有的**：日期格式、时间格式、日期合理性（比如 `2026-13-45` 也能进）。

### 实测模型表现

隐性触发实验里：
- 「下周四 2026-11-05 下午 3 点」→ `date="2026-11-05"` ✅
- 「明天上午十点」（今天是 2026-10-29）→ `date="2026-10-30"` ✅ **正确换算**

⇒ 模型自觉遵守，但没有兜底。

```js
// event-store.append() 构造 checkpoint
// 四段（goal/state/dead/next）全空也接受
```

89% 的历史数据四段为空，硬拒会让写入节奏断裂。

## 五、WAL 半渡态：判据门的时序问题

```
memory_note(kind=handoff) 的执行顺序（lib/index.js:21935-22010）：

  Phase 1  appendHandoffCheckpointPre(...)   ← 先写事件，零内容校验
  Phase 2  writeHandoffLedger(...)           ← 再过判据门，不合格 ok:false
  Phase 3  失败 → 追加 kind='handoff-write-failed' 补偿检查点
```

**问题**：Phase 1 已经把内容写进事件库了（不可撤销），Phase 2 才校验格式。

**实测后果**：
- 账本 `.md` 没写（好）
- 但坏内容作为**不可撤销的检查点**留在了事件库
- 每失败一次多两条（坏内容 + 补偿标记）

**真实数据**：`write-failed` 补偿标记 = **3 条** ⇒ 真实发生过 3 次。

**Phase 3 的文案自己就承认了**：
> 「原内容已作为前一检查点记入事件（可经 memory_recall(scope="events") 取回）。」

## 七、结论

**校验能力是有的，只是分布极不均衡：**

```
账本         ████████████████████  H1-H4 强判据 + S1-S4 软判据
白板         ██                    P-H1/P-H2（刻意最弱）
日历         ████                  标题 + 象限
userPercept  █                     stage 枚举
检查点        ·                     无
感知其余字段  ·                     无
```

**这不是"没实现"，是"只在对的地方实现了"。**

账本之所以有强判据，是因为它是最重要的原文载体（跨窗口交接的唯一凭据）。
其余面没有，是因为设计上假设「模型会自觉」。

**实测表明模型确实自觉**（15/15、10/10），
但**这正是危险之处** —— 一旦提示词被精简，自觉就失去了依据。

## 安全边界

**套件的最高纪律：绝不写真实记忆库。**

四层防线：

1. **配置隔离** —— `memoryRoot` / `userMemoryDir` 指向沙箱绝对路径（`~` 会被 `os.homedir()` 展开，`DSH_HOME` 拦不住）

跑完可用 `node lib/report.mjs` 查看违规汇总；真实库工作区数基线记在 `<WORK>/.real-workspace-count`。

## 一、环境与驱动

### 1. 插件在 headless 下永远 pending

```
dsh: warning: 1 entry did not activate
auto-memory-pre (@a9i5k4/dsh-auto-memory): pending (waiting for service: webServer)
```

**根因**：插件 `lib/index.js` 里 `export const inject = ['webServer','tools','systemPrompt','subagents','llm']`，而 `dsh-headless` 层不挂 Host/HTTP ⇒ `webServer` 服务不存在。

**修法**：patch 层补一行最小 webserver（`setup/init-profile.mjs` 已自动化）。

**症状的迷惑性**：命令 exit 0、输出正常、模型也回复了 —— 只是**一个记忆工具都没有**。所有相关测试都会静默失败。

### 2. `memoryRoot` 的 `~` 逃出 `DSH_HOME`

```js
// lib/index.js 的默认配置
memoryRoot: '~/.dsh/memory/workspaces',
```

```js
expandUserPath(p) {
  if (p.startsWith('~/')) return path.join(homedir(), p.slice(2))  // ← os.homedir()
}
```

**`DSH_HOME` 完全拦不住它** —— 会直接写进真实记忆库。

**修法**：显式覆盖成沙箱绝对路径。`setup/init-profile.mjs` 会做，`lib/lint.mjs` 每次检查。

### 3. 提权后沙箱反而崩

```
Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(C:\Windows\System32)
```

**根因**：`dsh-sandbox` 的 `writableRoots(policy)` 包含 `tmpdir()`。提权后 `TEMP` 变成 `C:\Windows\System32`，而该目录受 TrustedInstaller 保护 ⇒ `grantWrite()` 必然 Win32 error 5。

**症状极具误导性**：**连工作区内的正常写入都失败**，看起来像"沙箱坏了"，实际是"沙箱装不起来"。

**修法**：运行器强制把 `TEMP`/`TMP`/`TMPDIR` 指到可写目录（`lib/config.mjs` 的 `SANDBOX_ENV`）。

### 4. 未提权时 `grantWrite` 失败

`D:\` 下继承的权限是 `Authenticated Users:Modify`，**不含 `WRITE_DAC` / `WRITE_OWNER`**，而 ACL 沙箱要改 DACL + 完整性标签 ⇒ Win32 error 5。

**修法**：`setup/elevate.ps1`（会弹 UAC，一次性）。

### 5. Windows 上 `spawn` 的三个坑

| 写法 | 结果 |
|---|---|
| `spawn('dsh', [...], {shell:true})` | exit 0、0 秒、**无任何输出**（Git Bash 的 sh 把命令吃了） |
| `spawn('dsh.cmd', [...])` | `EINVAL`（Node 24 不允许直接 spawn .cmd） |
| `spawn(process.execPath, [binJs, ...])` | ✅ 唯一稳定路径 |

### 6. 路径里的 `\n` 被当转义

```js
dshCmd: 'C:\Users\...\npm\node_modules\...'
//                ↑ `\n` 在这里是换行符
// 报错：Cannot find module 'C:\Users<user>AppDataRoaming
pm
ode_modules...'
```

**纪律**：内部路径一律用正斜杠。

## 二、取数据

### 7. 会话日志是多帧 zstd

`session.v4.jsonl.zstd` 是**一帧一行**追加写的。单次 `zstdDecompressSync` 只能拿到第一行。

**修法**：按 magic `28 b5 2f fd` 切分后逐帧解压（`lib/driver.mjs` 的 `readSessionEvents`）。

### 8. 三种事件形状

| 来源 | 调用 | 结果 | callId 位置 |
|---|---|---|---|
| NDJSON | `{type:'tool_call', tool, input}` **平铺** | `{type:'tool_result', callId, result}` | `d.callId` |
| 会话日志 | `{type:'tool/call', data:{name, arguments}}` **嵌套** | `{type:'tool/result', data:{message:{...}}}` | `d.message.toolCallId` |
| `arguments` 是 **JSON 字符串** | 要 `JSON.parse` | | |

`lib/driver.mjs` 的 `flat(x)` 统一两种形状。

### 9. `usage` 是平铺的

```js
// ✗ 错
rows.filter(x => x.data?.phase === 'step_end').map(x => x.data.usage)
// ✓ 对
rows.filter(x => x.type === 'status' && x.phase === 'step_end').map(x => x.usage)
```

**后果**：token 全记成 0，于是「省了多少 token」这个核心论断没有数据支撑，白跑 45 次。

### 10. 输出采集器读到 `undefined`

同一个根因（形状没兼容）。症状是 `tool | undefined(undefined)` —— 看起来像采集器坏了，实际是字段名不对。

## 三、判分（最贵的坑，静默失败过 5 次）

> 这一节每一条都曾把**完全正确的模型**判成 0 分，而且表面看像"模型不行"。
> 这就是为什么 `lib/selftest.mjs` 必须有 22 项断言。

### 11. 拿最终文本评分

模型按纪律调 `memory_note` 把账本写进文件，最终文本只是"完成 / 已写入 handoff-xxx.md"。

⇒ 必须取 **`memory_note` 的 `content` 入参**。

### 12. 取最后一版而不看结果

模型常先写一版被 H1 拒、读到回执后自己改对。

⇒ 必须取**最后一次 `result` 为成功**的那版；一次都没成功才取最后一次调用（这样"始终没改对"会被如实记为失败）。

### 13. `isOk` 全仓搜 "error"

模型在一次成功写入之后又调一个失败的 `pwsh` ⇒ 成功的那次被判成失败。

⇒ 只认「该工具自己的回执开头明确宣告失败」（`lib/driver.mjs` 的 `isOk`）。

### 14. `memory_procedure.steps` 不是数组

```js
// schema 里写的
steps: { type: 'string', description: '流程步骤，**一行一步**（换行分隔）…' }
```

判分器按数组判 ⇒ 一个完全正确的调用被判 FAIL。

⇒ **判分必须照 schema，不能照直觉。**

### 15. `ev-create` 里的 append 要区分目标

模型 `create` 新事件后立刻往里 `append` 检查点是**正确做法**；只有 append 到**旧** eventId 才算误挂。

⇒ 判据必须排除旧 id（`lib/judge.mjs` 的 `appendOld`）。

### 16. 白名单：宿主心跳会被当成 agent 越界

`polling-heartbeat.json` / `notices-cache-pre.json` / `update-check-pre.json` 由**桌面宿主进程**周期性写，与 agent 无关。

⇒ 不加白名单会产生 100% 固定误报（实测 157 份报告里 2 份误报），反而掩盖真问题。

## 四、夹具

### 17. 夹具必须写到**沙箱记忆库**，不是 cwd

```js
// ✗ 错：插件根本不读这里
fs.writeFileSync(path.join(cwd, 'handoff', 'PLAN.md'), ...)

// ✓ 对
fs.writeFileSync(path.join(projectDirOf(cwd), 'handoff', 'PLAN.md'), ...)
```

**写错位置的后果链**（实测）：
1. `memory_read(kind=plan)` 返回 `content: ""`、revision 是空串的 sha256
2. `memory_recall(scope=events)` 说「本工作区还没有任何事件」
3. 模型于是去文件系统翻找 —— **39 个工具调用、240 秒超时**
4. 还翻到了别的实验工作区的 `PLAN.md` 和我的实验日志（自指污染）

### 18. 一个坏事件会毒死整个事件库

```
memory_event 失败: 事件写入前校验失败(evt_abc12345): missing:skillRef,bad-kind:task
```

`validateEventPre` 是 fail-closed 的 26 字段校验，但它把「库里所有事件」和「本次写入」混在一起报。

**后果不是「那个事件被拒」，而是整个 store 的每次写入都失败** —— 包括新建另一个事件。模型连续 3 次 create 全被挡住。

⇒ `lib/fixtures.mjs` 的 `makeEvent()` 强制合法化 `kind`/`confidence` 并补齐 26 字段；`lib/selftest.mjs` 有 3 项断言守着。

合法 `kind` 枚举：`ledger / planSnapshot / sessionTranscript / project / mechanical / unknown`

## 五、实验设计

### 19. 任务语料必须自包含

首版从真实账本反推任务描述，模型把「帮我写账本」理解成「先去仓库查这件事」，于是 `read <repo>\lib\index.js`、`pwsh Get-ChildItem`、`memory_recall` 去核实，单条跑到 **28 步 / 300 秒超时**。

⇒ 任务里直接给全部素材，并显式禁止调用 `memory_note` 以外的工具。单条耗时 300s → 17–35s。

### 20. 并发不能太高

`grantWrite` 会写目录 ACL（加锁），并发超过 4 会互相干扰；本地 LLM 网关也可能限流。默认 3。

### 21. 提示词只有一个层可改

`promptLayerOverrides` 能改 27 个动态层，但 `renderMemoryStatic()`（6,220 字符，含四段规则/四类感知/技能库/看板 tag）是**硬编码**的 —— 改不到。

⇒ 「精简静态纪律」这个变量测不了。想测必须先改产品代码。这是套件的**已知盲区**。

## 附：诊断顺序

环境跑不通时，按这个顺序查，能最快定位：

```
1. node setup/preflight.mjs          ← 9 项检查，每项给可执行的修法
2. node lib/selftest.mjs             ← 判分器坏了吗
3. node lib/lint.mjs                 ← 产品改了、套件还准吗
4. 单条手跑：
   DSH_HOME=<work>/dshhome TEMP=<work>/tmp \
   node <dsh-bin> --profile memexp --json "回复 OK"
   期望看到：[dsh-auto-memory] ready: engine + 21 tools + ...
5. 看逐条输出：<work>/live/output/<tag>.jsonl
```

看到 `pending (waiting for service: webServer)` ⇒ 坑 #1。
看到 `SetNamedSecurityInfoW failed (Win32 5)` ⇒ 坑 #3 或 #4。
看到模型在 `pwsh Get-ChildItem -Recurse` ⇒ 坑 #17（夹具放错位置）。
